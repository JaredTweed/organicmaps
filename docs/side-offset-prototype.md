# Side-offset visual prototype

This experimental prototype is saved on `prototype/cycling-side-offsets` on
JaredTweed's fork at the user's request. It is not part of the split PRs and
does not change #12692. Saving the branch does not make it a merge candidate.

## Behavior

- Ordinary roads retain their primary highway styling. Explicit left/right
  or both-side cycling facilities are rendered alongside that road.
- Dedicated cycleways retain their core-line treatment.
- Solid track, dashed lane and dotted shared-lane strokes reuse the existing
  cycling drawing rules at full stroke scale, with a visible gap from the road.
- Dedicated cycleways/designated shared paths and unlocated cycling overlays
  retain cycling-style core widths even in the default map style; they must
  not fall back to the generic style's hairline cycleway treatment.
- Explicit side-specific tags override both-side tags; reversed OSM geometry
  swaps sides and reverses stored directions. Separately mapped facilities
  are not duplicated by attached offset strokes.
- Unqualified tags without explicit sides retain the existing centerline
  fallback. This prototype does not guess an unrecorded side.
- Generic and cycling styles can both display the offset strokes.

## Deliberate limits

This is not a production data-model or routing proposal. The demo map uses
the existing test-only metadata field, with a versioned payload, rather than
consuming more classifier slots or inventing extra highway types. Production
side storage needs its own reviewed schema. The prototype preserves explicit
side directions but does not add per-side arrows. It does not change routing
access flags. Offset joins, intersections, changing road widths and phase
across differently tagged ways still need production design and review.

Offset geometry uses the existing spline equidistant implementation before
tile clipping. Its acute-angle limitations are not resolved by this demo.
The map is a road-only Vancouver fixture, not a routable production download.

## Phone

Install separately as `app.organicmaps.cyclingsides.debug`, labeled
`OM Side Offsets`. Do not replace the normal app or the centerline demo.

The included `side-offset-examples.kml` category provides six real OSM
locations. Side means relative to OSM way direction, not screen left/right.
Inspect at street-level zoom; the offset overlay begins at zoom 14.

- Water Street: lane on one side and shared lane on the other.
- West 49th Avenue: lane on one side and track on the other.
- East 14th Avenue: shared lanes on both sides.
- West 1st Avenue: a one-sided lane.
- Ash Street: lanes on both sides.
- East 5th Avenue: a one-sided track.

Coordinates and tag examples come from the local Vancouver OSM fixture, not
a claim that these are current on-the-ground infrastructure conditions.

## Build and map workflow

The source includes the isolated-app-ID option and the
`sideOffsetPrototypeJni` option for packaging a separately built native
library. Do not install this fixture into the normal Organic Maps package.

1. Configure a Debug Android arm64 CMake build with the repository's NDK/SDK.
   The tested native setup used `-O0 -g0`, unity batch size 5, and the historical
   `map` target's original unity batch size 50. Build `organicmaps` with `-j1`.
   Keep heavy jobs sequential with a 1800 MiB hard memory cap and no swap use.
2. Put the resulting `liborganicmaps.so` under `<jni-dir>/arm64-v8a/`.
   Build the separate APK from `android/`, for example:

   ```sh
   ./gradlew :app:assembleGoogleDebug --no-daemon --max-workers=1 --no-parallel \
     -Parm64 -PresearchApplicationId=app.organicmaps.cyclingsides \
     -PsideOffsetPrototypeJni=/absolute/path/to/jni-dir \
     -Pkotlin.compiler.execution.strategy=in-process \
     '-Dorg.gradle.jvmargs=-Xmx640m -Xms128m -XX:MaxMetaspaceSize=320m -XX:ActiveProcessorCount=2'
   ```

3. A new map needs the side metadata generated by this branch; a stock map
   cannot recover the discarded left/right tags. The helpers in
   `docs/cycling-tag-audit/` build an exporter from a configured host
   `generator_tool` build, generate the one-worker Vancouver fixture and
   record source/resource checksums. Use their `--help` options for paths.
   The recorded road-only OSM input SHA-256 is
   `d034b4a5f1758e0b856b5bc09057e79200853f2970f5a12cb1ba927881c9ce08`.
4. For the packaging/capture helper, explicitly set
   `OM_VISUAL_PACKAGE=app.organicmaps.cyclingsides.debug`. Package with the
   matching native/map manifests, Android build tools and debug keystore.
   The helper updates the fixture catalogue size and verifies signatures,
   resources and checksums. Renderer-only map reuse is permitted only for
   this isolated prototype and is checked against the pinned Git revisions.
5. Install with `adb install -r` to preserve demo data. Place the fixture in
   the catalogue-version directory under the demo app's private `files/`
   storage, and put the example KML under its `files/bookmarks/` directory.
   Use the capture helper's `--prototype-cameras` only for prototype camera
   setup, not reference-equivalence validation. Captures are optional.

The included tooling's configuration/safety tests can be run without a build
or connected phone:

```sh
python3 -m unittest discover -s docs/cycling-tag-audit -p 'test_*.py'
```
