# Transit adapter prototypes

## Winnipeg Transit realtime adapter

Winnipeg Transit publishes standard static GTFS, but its realtime predictions are exposed through the city's Open Data Web Service rather than a public GTFS-Realtime endpoint.

Organic Maps' transit preview/backend already requests realtime updates **per stop**. Winnipeg's `GET /v4/stops/{stop}/schedule.json` endpoint is also stop-scoped, so it can be adapted without polling every Winnipeg stop or constructing a city-wide pseudo-GTFS-RT feed.

`winnipeg_realtime_adapter.py`:

- requests API v4 with `json-camel-case=true`;
- accepts both camelCase and legacy hyphenated Winnipeg JSON;
- emits normalized updates with GTFS-style `trip_id`, `route_id`, `stop_id`, cancellation state, and arrival/departure delays in seconds;
- optionally validates/resolves Winnipeg `trip-key` values against the static GTFS zip;
- refuses to guess when a proprietary trip key cannot be mapped uniquely.

### Example

```bash
python tools/python/transit/winnipeg_realtime_adapter.py 10064 \
  --api-key "$WINNIPEG_TRANSIT_API_KEY" \
  --gtfs google_transit.zip
```

For offline testing with a captured response:

```bash
python tools/python/transit/winnipeg_realtime_adapter.py 10064 \
  --input stop-10064.json \
  --gtfs google_transit.zip
```

### Why stop-scoped translation

Winnipeg Transit limits each API key/IP to 100 requests per minute. Polling every stop to manufacture a complete GTFS-Realtime feed would therefore be slow and wasteful. A per-stop adapter matches Organic Maps' existing `/updates/{stopId}` access pattern and only queries realtime data the client actually requests.

### Upstream integration

The deployed schedules/realtime service (`pt.organicmaps.app/api/v1`) is generated by the separate `gtfs-parser` backend referenced by `gtfs-osm-matcher`; that backend is not currently present in the public Organic Maps repositories. The intended upstream integration is therefore to port this normalization logic into that service and register Winnipeg as a non-GTFS-RT realtime provider.

Before enabling production use, verify against one live API response that Winnipeg's `trip-key` is identical to static GTFS `trip_id`. If it is not, keep the supplied GTFS resolver/fallback or implement the equivalent mapping in the backend's native language.
